# Develop and release

## Layout

The repository holds a Rust workspace (`Cargo.toml`: the crates) and a Bun workspace (`package.json`: the package,
the demo, the benchmark, the examples, these docs), side by side at the root, with their tools: `rustfmt.toml` for
Rust, `biome.json` (format and lint) and `tsconfig.base.json` for TypeScript.

```
crates/geo/        camera and projections, geodesy (WGS 84, Moon, Mars), RAF20 geoid, tile selection, label placement,
                   polygons
crates/tiles3d/    3D Tiles tree, traversal and decoding (meshopt, quantization, b3dm, pnts, glb)
crates/pointcloud/ point clouds: COPC (LAS header, octree hierarchy, LAZ chunks), the octree traversal; the LAZ
                   decoder is built apart, the point cloud module of the workers
crates/engine/     the WebAssembly core: the engine, the ground, the layers (render/), picking; built twice, with and
                   without the 3D Tiles (its `tiles3d` feature)
packages/isard/    the npm package isard: GeoMap, layer handles, overlays, workers
apps/demo/         the demo; apps/bench/: isard, iTowns and 3DTilesRendererJS on the same scenario; apps/viewer/: the
                   viewer of local files and its bridge (bun scripts/viewer.ts serves it)
examples/          one page per example, as an application would write it
docs/              this site (VitePress)
scripts/           build (and its size budget), dev server, release
```

### The package's sources

```
packages/isard/src/
  index.ts, formats.ts, projections.ts, geoplateforme.ts   the entry points (isard, isard/formats…)
  map.ts, settings.ts, types.ts                            GeoMap, its options and public types
  map/         GeoMap's parts: the layers' order, overlays and controls, frame loop, hover picking, engines, workers
  engine-loader.ts                                         the engines and workers loaded (assetsUrl), at the root:
                                                           their URLs are next to it in dist and in bundles
  engine/      the decoding workers' pool and protocol, the decoders, the request headers
  layers/      the layer handles: features, extrusions, labels (glyphs, icons), point clouds, panoramas
  basemap/     basemaps, vector tiles and styles, MVT, PMTiles, the relief, rasters reprojected, WMTS grids
  data/        CRSs and formats: KML, GPX, TopoJSON, XML
  ui/          markers, popups, panels, controls, their CSS, the mouse, touch and keys
  util/        geodesy, colors, animations, an LRU
  bind/        what the framework bindings share, free of any framework: a layer's changes, their order
  react/       isard/react: the components and hooks
  workers/     the two workers (bundled on their own)
  wasm/        the engines' bindings (generated by the build)
packages/isard/test/   the same folders, a test per module (fakes.ts: the engine and the DOM faked)
packages/isard/vite.js the Vite plugin (isard/vite)
```

`crates/geo`, `crates/tiles3d` and `crates/pointcloud` have no WebGL and no I/O; `crates/engine` keeps its WebGL and
browser calls apart from its logic (raster cache, 3D Tiles state, styles, placement): all four are tested natively. The package's pure
modules (MVT, style expressions, colors, glyphs) are tested by `bun test`.

## Commands

Requires Rust (the version of `rust-toolchain.toml`, which rustup installs with its components and the
`wasm32-unknown-unknown` target), `wasm-bindgen-cli` at the version of the `wasm-bindgen` crate in `Cargo.lock` (the
build stops with the command to install it otherwise), and Bun.

```sh
bun install
bun run dev          # builds, then serves the demo on :5180, the benchmark on /bench/, the examples on /examples/
bun run build        # the engine, the package, the demo and the examples; build:bench adds the benchmark
bun run test         # Rust tests, then the package's (bun test)
bun run lint         # Biome, rustfmt, clippy pedantic (native and wasm), warnings as errors
bun run typecheck    # strict TypeScript
bun run docs:dev     # this site, with the examples live and the API reference generated
bun run docs:check   # the API reference: every type a public signature uses is exported
```

The checks run on every push and pull request; the site is deployed once they pass on `main`.

`bun run build` ends with the sizes of what the package ships, gzipped: the two engines (`isard_core_bg.wasm`
without 3D Tiles, `isard_bg.wasm` with them), the point cloud module (`isard_points_bg.wasm`), the package's modules, the engines' bindings and the workers. Each has a
budget about 5 % above its size when it was set, in `scripts/size.ts`: over one, the build fails, and so do the
checks. A growth is then raised there deliberately, in the commit that makes the code bigger (`bun scripts/size.ts`
checks the last build again).

## Release

Raising the version is the release: set it in `packages/isard/package.json` and in the four `crates/*/Cargo.toml`,
describe it in `CHANGELOG.md`, check it, then push it to `main`.

```sh
bun run release:dry   # build, lint, types, tests, the package packed: its file list (nothing published)
```

Once the checks pass on that push, the Release workflow sees a version that is not on npm yet: it builds the package,
publishes it with provenance through npm's trusted publishing (no token on any machine), then tags the commit
`v<version>` with a GitHub release of its changelog section. The pushes that leave the version alone publish nothing.
`release:dry` stops if the changelog does not describe the version, a crate has another version, or the version is on
npm already. Trusted publishing is set up once on npmjs.com, in the package's settings (publisher: GitHub Actions, this
repository, workflow `release.yml`).
